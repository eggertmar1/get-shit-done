  <files>get-shit-done/references/config-resolution.md</files>
  <action>
Create a new reference document at `get-shit-done/references/config-resolution.md` that specifies the hierarchical config resolution algorithm for multi-project GSD. This is the core "config merger" specification that all GSD agents and commands will reference when reading configuration.

Follow the same XML-section markdown format used in path-resolution.md and shared-paths.md (sections wrapped in XML tags like `<overview>`, `<core_principle>`, etc.).

The document must include these sections:

**overview**: Config resolution merges global defaults with per-project overrides using shallow merge (project values replace global values for matching keys).

**core_principle**: "Read global, overlay project, project wins." Global config at `.planning/config.json` provides defaults. Per-project config at `projects/<name>/config.json` contains only overrides (sparse). Merge is shallow: top-level keys from project config completely replace global values.

**config_hierarchy**: Two scopes:
  1. Global: `.planning/config.json` (always exists, provides all defaults)
  2. Project: `.planning/projects/<active>/config.json` (optional, contains only overrides)

Resolution order: Global -> Project (project wins for matching keys).

**resolution_algorithm**: Pseudocode and bash implementation for resolving merged config. Include:
  - Read global config (always exists, fallback to `{}` if somehow missing)
  - Read .active file to find active project (use path-resolution.md pattern)
  - Read project config if exists (fallback to `{}` if missing -- lazy creation means most projects won't have one)
  - Shallow merge with jq: `jq -s '.[0] * .[1]'` (global as base, project overlay)
  - Extract specific value with jq: `echo "$MERGED" | jq -r '.["workflow.research"] // true'`
  - Note: Use dot-notation key access with jq bracket syntax since keys contain dots

**overridable_settings**: Table classifying each setting:

| Setting Key | Default | Overridable | Rationale |
|-------------|---------|-------------|-----------|
| `mode` | `"yolo"` | Yes | Workflow style is project-dependent (careful for critical, yolo for exploration) |
| `depth` | `"quick"` | Yes | Complex projects may need comprehensive planning |
| `parallelization` | `true` | Yes | Some projects may need sequential execution |
| `commit_docs` | `true` | Yes | Public/OSS projects may keep planning private |
| `model_profile` | `"balanced"` | Yes | High-priority projects may warrant quality profile |
| `workflow.research` | `true` | Yes | Simple projects can skip research |
| `workflow.plan_check` | `true` | Yes | Fast-iteration projects may skip plan checking |
| `workflow.verifier` | `true` | Yes | Quick fixes may skip verification |
| `git.branching_strategy` | `"none"` | Yes | Team projects need phase branches, solo don't |
| `git.phase_branch_template` | `"gsd/phase-{phase}-{slug}"` | Yes | Projects may need custom branch naming |
| `git.milestone_branch_template` | `"gsd/{milestone}-{slug}"` | Yes | Projects may need custom branch naming |
| `planning.search_gitignored` | `false` | No (global-only) | Search scope is repo-level, not project-level |

**lazy_creation**: Document that project config.json is NOT created during `/gsd:new-project`. It's only created when a user first overrides a setting via `/gsd:settings` with project scope. This keeps project directories clean. When reading project config and file doesn't exist, treat as empty `{}` (no overrides, use global defaults).

**flat_config_structure**: Document the flattened key format using dot-notation. CRITICAL section -- explain why:
  - Old nested format (`workflow: { research: true }`) is problematic with shallow merge because overriding one nested key replaces the entire parent object, losing sibling keys
  - New flat format uses dot-notation keys: `"workflow.research": true`, `"git.branching_strategy": "none"`
  - Each setting is an independent top-level key, so overriding `"workflow.research"` in project config doesn't affect `"workflow.plan_check"` or `"workflow.verifier"`
  - Include a migration note: existing configs with nested format still work (jq `*` merges objects), but new configs should use flat format. Eventually Phase 4 integration will update the settings command to write flat format.
  - Show both the old nested and new flat config.json examples side by side

**usage_patterns**: Show 3 common patterns:
  1. Reading a single config value (with default fallback)
  2. Reading merged config in a workflow/command
  3. Writing a config value to specific scope (global vs project)

**provenance_display**: Show how to display config with source annotation ("global" vs "project override") for the settings command's display mode. Similar to `git config --show-origin`.

**related_references**: Link to @path-resolution.md, @shared-paths.md, @planning-config.md
  </action>
