  <action>
Create a workflow document that defines the migration procedure. This is referenced by new-project.md when migration is triggered.

Include these sections:

1. **When This Workflow Runs**:
   - User runs `/gsd:new-project` on repo with existing flat `.planning/` structure
   - User confirms they want to migrate to multi-project
   - User provides name for the migrated project

2. **Pre-Migration Checks**:
   ```bash
   # Verify flat structure exists
   test -f .planning/PROJECT.md && ! test -d .planning/projects

   # Ensure working directory is clean (or warn)
   git status --porcelain
   ```

3. **Migration Steps** (in order):

   **Step 1: Gitignore .active FIRST** (critical - from CONTEXT.md)
   ```bash
   # Add .active to gitignore BEFORE creating any structure
   echo ".active" >> .planning/.gitignore
   git add .planning/.gitignore
   git commit -m "chore: gitignore .active file for multi-project support"
   ```

   **Step 2: Create project structure**
   ```bash
   mkdir -p .planning/projects/{PROJECT_NAME}
   ```

   **Step 3: Move project-specific files with git mv** (preserves history)
   ```bash
   # These files are project-specific - move them
   git mv .planning/PROJECT.md .planning/projects/{PROJECT_NAME}/PROJECT.md
   git mv .planning/REQUIREMENTS.md .planning/projects/{PROJECT_NAME}/REQUIREMENTS.md
   git mv .planning/ROADMAP.md .planning/projects/{PROJECT_NAME}/ROADMAP.md
   git mv .planning/STATE.md .planning/projects/{PROJECT_NAME}/STATE.md
   git mv .planning/phases .planning/projects/{PROJECT_NAME}/phases
   git mv .planning/research .planning/projects/{PROJECT_NAME}/research
   git mv .planning/todos .planning/projects/{PROJECT_NAME}/todos

   # Note: Some files may not exist - that's OK, use `git mv` with error handling
   ```

   **Step 4: Handle config.json** (copy, don't move)
   ```bash
   # Original becomes global defaults
   # Copy becomes per-project overrides
   cp .planning/config.json .planning/projects/{PROJECT_NAME}/config.json
   ```

   **Step 5: Shared files stay at root**
   - `.planning/codebase/` - stays (shared across projects)
   - `.planning/config.json` - stays (becomes global defaults)

   **Step 6: Set active project** (after gitignore is committed)
   ```bash
   echo "{PROJECT_NAME}" > .planning/.active
   ```

   **Step 7: Commit migration**
   ```bash
   git add .planning/projects/{PROJECT_NAME}/
   git commit -m "refactor: migrate to multi-project structure

   Migrated existing planning files to projects/{PROJECT_NAME}/

   Project-specific files moved:
   - PROJECT.md, REQUIREMENTS.md, ROADMAP.md, STATE.md
   - phases/, research/, todos/
   - config.json (copied for per-project overrides)

   Shared files remain at .planning/ root:
   - codebase/ (repo-level analysis)
   - config.json (global defaults)

   Active project set to: {PROJECT_NAME}
   "
   ```

4. **Error Handling** (from CONTEXT.md - best effort):
   - If any `git mv` fails, report which files failed
   - Don't attempt rollback (too complex)
   - Guide user to manually fix via git commands
   - Example: "Failed to move phases/. Check if directory exists and try: git mv .planning/phases .planning/projects/{NAME}/phases"

5. **Post-Migration Verification**:
   ```bash
   # Verify structure
   test -d .planning/projects/{PROJECT_NAME}
   test -f .planning/projects/{PROJECT_NAME}/PROJECT.md
   test -f .planning/.active
   test -d .planning/codebase  # Still at root

   # Verify .active is gitignored
   git check-ignore .planning/.active
   ```

Follow the format of existing workflows like `execute-plan.md`.

```markdown
## Check for Existing Planning Structure

Before creating a new project, check if a flat `.planning/` structure already exists:

1. Check for flat structure:
   ```bash
   # Flat structure = PROJECT.md exists AND projects/ doesn't exist
   test -f .planning/PROJECT.md && ! test -d .planning/projects
   ```

2. If flat structure detected, **offer migration** (don't auto-migrate):

   Show the user what exists:
   ```
   Found existing planning structure:
   - .planning/PROJECT.md
   - .planning/ROADMAP.md
   - .planning/STATE.md
   - .planning/phases/
   [list actual files found]

   This looks like a single-project setup. To support multiple projects,
   these files can be moved to .planning/projects/<name>/.

   Shared files will stay at root:
   - .planning/codebase/ (repo-level analysis)
   - .planning/config.json (global defaults)
   ```

3. Ask user for decision:
   ```
   Would you like to:
   A) Migrate to multi-project structure (recommended for teams)
   B) Continue with existing single-project structure

   If migrating, what should the project be named?
   Suggestion: Use descriptive name like "main-app" or "api-refactor"
   ```

4. If user chooses A (migrate):
   - Get project name from user (do not assume "default")
   - Reference @migrate-to-multiproject workflow
   - Execute migration steps
   - Confirm success

5. If user chooses B (keep flat):
   - Proceed with normal new-project flow (existing behavior)
   - Note: They can migrate later by running /gsd:new-project again
```
